= RAD Statecharts Template
:toc: macro

A UI-agnostic starting point for a full-stack https://github.com/fulcrologic/fulcro-rad[Fulcro RAD] app using
https://github.com/fulcrologic/fulcro-rad-statecharts[fulcro-rad-statecharts]: forms, reports and routing are driven by
statecharts instead of UI state machines and dynamic routing.

Derived from https://github.com/fulcrologic/fulcro-rad-template[fulcro-rad-template].

toc::[]

== What's in the box

[cols="1,3"]
|===
| Client | Fulcro 3.10 + RAD 1.6 + `fulcro-rad-statecharts`. One routing statechart (`ui/routes.cljc`) is the router.
| Rendering | `com.example.ui.render.*`: plain HTML renderers, *owned by this app* (no UI plugin library). Restyle them with your design system.
| Server | http-kit + Ring, Pathom 2 with RAD's generated resolvers, `mount` for lifecycle
| Database | Datomic via the client API (`fulcro-rad-datomic`). In-memory in dev, on-disk Datomic Local in prod.
| Auth | Users with email/password login (bcrypt hashes in Datomic), every API call guarded, REPL/CLI user management. Easy to remove. See <<Authentication>>.
| Tests | Headless end-to-end tests: real client + real Ring handler + parser + in-memory Datomic in one JVM. No browser.
| Deploy | `build.clj` uberjar, `Dockerfile`, `config/prod.edn` driven by env vars
|===

Not included (deliberately): roles/permissions, sign-up and password reset, file uploads (RAD blob support), a CSS framework.

== Start a new project

[source,bash]
----
./rename-project.sh com.my-domain.app-name   # use hyphens, not underscores
pnpm install                                 # npm/yarn are refused
----

A `mise.toml` pins Java 21, Clojure and Node 24 (`mise install`). pnpm is provided by corepack (`corepack enable`).

== Development

[source,bash]
----
make cljs             # shadow-cljs server; start the `main` watch at http://localhost:9630
----

[source,bash]
----
$ clj -A:dev
user=> (require 'development)
user=> (development/start)    ; server on http://localhost:3000, seeded in-memory Datomic
                              ; log in as dev@example.com / letmein
user=> (development/restart)  ; stop, reload source, start
----

`make test` runs the headless end-to-end tests (`src/test/com/example/app_test.clj`).

== How the pieces fit

* *Model*: RAD attributes in `model_rad/`, hand-written resolvers in `model/`. Unchanged from standard RAD.
* *Forms and reports*: `defsc-form` / `defsc-report` from `com.fulcrologic.rad.statechart.form` / `.report`.
  Option keys (`fo/`, `ro/`) are the standard RAD ones.
* *Routing*: every page is a state in `routing-chart` (`ui/routes.cljc`). Navigate with `scr/route-to!`,
  `form/edit!`, `form/create!`. URLs come from `:route/segment` in the chart; `fo/route-prefix` and `ro/route`
  are ignored.
* *Unsaved changes*: leaving a dirty form puts the routing chart in `:routing-info/open`; `Root` shows a prompt
  calling `scr/abandon-route-change!` or `scr/force-continue-routing!`.
* *Rendering*: requiring `com.example.ui.render.plugin` registers `defmethod`s on RAD's rendering multimethods.

=== Adding a design system (e.g. Tailwind + DaisyUI)

1. Add your CSS build (e.g. the Tailwind CLI with DaisyUI) writing to `resources/public/css/main.css`,
   and uncomment the stylesheet link in `components/ring_middleware.clj`.
2. Add classes in `ui/render/*.cljc` (`input input-bordered`, `btn btn-primary`, `table`...). Write full,
   literal class strings: Tailwind only finds classes it can see in the source. Point its `content` at `src/**/*.cljc`.
3. Keep the `data-rad-*` attributes; the tests use them.

== Authentication

* *Users*: a `user` entity (`:user/id`, `:user/email`, `:user/password-hash`, `:user/active?`), separate from your
  own entities. It is plain Datomic schema in `components/auth.clj`, deliberately *not* RAD attributes: RAD generates
  resolvers for its attributes, which would let any client query the hashes. Passwords are bcrypt hashes
  (`buddy-hashers`).
* *Sessions*: the logged-in user id is stored in the encrypted session cookie (see Deployment, `SESSION_KEY`).
  Login rotates the session id to prevent session fixation.
* *Guard*: `auth/guard-plugin` (a Pathom plugin) refuses every resolver and mutation to anonymous requests except
  `login`, `logout` and `:session/current-user`. Add role or ownership checks there.
* *Client*: `com.example.session` asks the server who is logged in at startup. Routing only starts once someone is
  logged in; in the browser, URL sync then restores the URL the user arrived on. Logout reloads the page.
* *Not covered*: login rate limiting / lockout, sign-up, password reset, roles, and revoking sessions (a disabled
  user can't log in again, but a session they already have stays valid until logout or `SESSION_KEY` rotation).

=== Managing users

From a REPL (dev or a REPL attached to production):

[source,clojure]
----
(require '[com.example.components.auth :as auth])
(auth/add-user! "me@example.com" "a long password")
(auth/set-password! "me@example.com" "another one")
(auth/set-active! "me@example.com" false)   ; disable / re-enable login
(auth/users)
----

Without a REPL (e.g. on a server or in a container), with the uberjar. It uses `config/prod.edn` like the server,
and prompts for the password (or reads it from stdin when piped), so it stays out of shell history:

[source,bash]
----
java -cp app.jar clojure.main -m com.example.components.auth-cli add-user me@example.com
java -cp app.jar clojure.main -m com.example.components.auth-cli set-password me@example.com
java -cp app.jar clojure.main -m com.example.components.auth-cli disable me@example.com   # or enable
java -cp app.jar clojure.main -m com.example.components.auth-cli list
----

With Datomic Local, stop the server first: its storage is meant to be used by one process at a time.
`make add-user EMAIL=me@example.com` does this for the `./data` database used by `make run-jar`.

=== Removing authentication

Authentication is self-contained, for apps that don't need users. Sessions (and CSRF protection) stay; they're
general infrastructure.

1. Delete `src/main/com/example/components/auth.clj`, `auth_cli.clj`, `src/main/com/example/session.cljc`,
   `src/main/com/example/ui/login.cljc` and `src/test/com/example/auth_test.clj`.
2. `grep -rn "AUTH:" src deps.edn Makefile` and do what each comment says (remove the line, or the replacement it
   describes).
3. Remove `buddy-hashers` from `deps.edn` (tagged), and this section and the `Auth` row from the README.

== Deployment

The app is a single JVM process: http-kit serves the API and the compiled JS.

[source,bash]
----
make uberjar          # shadow-cljs release + target/app.jar
make run-jar          # runs it with config/prod.edn, Datomic stored in ./data
make docker           # or build the image
----

Runtime configuration (`config/prod.edn`, deep-merged over `config/defaults.edn`):

[cols="1,3"]
|===
| `PORT` | HTTP port
| `DATOMIC_STORAGE_DIR` | Absolute path for Datomic Local storage. *Must be persistent* (a volume); the Docker image uses `/data`.
| `SESSION_KEY` | *Required.* 32 hex chars (`make session-key`) encrypting the session cookie. Nothing is stored server side, so sessions survive restarts and work across instances. Keep it stable and secret; changing it logs everybody out.
| `SECURE_COOKIES` | Unset = `true` (cookie sent over HTTPS only). Set `false` only to test over plain HTTP (`make run-jar` does).
| `-Dconfig=/path.edn` | Replace `prod.edn` entirely, e.g. to point at Datomic Pro or Cloud instead of Datomic Local
|===

The schema is created/migrated automatically from your attributes at startup. If startup fails (e.g. no
`SESSION_KEY`), the process exits with code 1.

Things to decide before going to production:

* *TLS*: terminate at a proxy/load balancer (HSTS is on, `:ssl-redirect` is off).
* *Datomic topology*: Datomic Local is a single process writing to local disk, so run exactly one instance.
  Scaling out means Datomic Pro (transactor + storage) or Datomic Cloud.
* *Auth*: review <<Authentication>> for what's not covered (rate limiting, sign-up/reset, roles). Create the first
  user with the CLI before going live.
